# Spotter Capabilities Audit — 2026-07-28

Scope requested: (1) the AI-Coach features, (2) the structure of program adding, (3) general
layout/flow, and (4) features worth adding to make the app feel worth paying for. Three deep
passes were run over the codebase (server + Android); the six highest-severity findings were
re-verified line-by-line in source before publication (marked **[verified]**).

**Severity legend:** 🔴 bug / data loss · 🟠 broken flow or dead end · 🟡 friction / gap · 🔵 opportunity

> **Resolution status (2026-07-28): Tiers 1, 2 and 3 are all delivered.** See the two
> "Audit Resolution Log" sections in CLAUDE.md for the full ledger.
> - **Tier 1** — superset wipe, chat poisoning, progression Apply + routine write-back, Home
>   blank state / routine reachability / preset discoverability, Reset-Account onboarding, error
>   surfacing with retry, completed-session detail, cardio summary + history.
> - **Tier 2** — exercise detail (instructions + secondary muscles for all 81 seeded movements,
>   history chart, PRs), RPE + set types with warm-up exclusion, manual mid-workout exercise
>   management, set deletion, rest-timer controls, data export, Health Connect.
> - **Tier 3** — post-workout AI debrief, weekly recap, proactive coach signals on Home,
>   periodized programs with scheduled deloads the coach can author, preset previews, and
>   workout templates ("repeat" / "save as routine").
>
> **Two items were deliberately NOT built**, rather than shipped hollow: **cardio GPS/pace**
> (needs real device sensors — unverifiable here) and **exercise demo images/video** (no licensed
> media source; the instructions backfill is the honest version). Both are recorded in CLAUDE.md.

## 1. Executive summary

The fundamentals are genuinely strong — better than most commercial apps at the same layer:
drift-free background-correct timers, real offline logging with reconnect sync, a correct
double-progression engine with deload detection, a disciplined server-side AI guardrail stack,
and a coherent design system. The weaknesses cluster in three themes:

1. **Surfacing.** Data and intelligence the app already computes never reach the user: errors
   are swallowed silently in at least five flows, progression advice is a display-only chip,
   completed workouts can't be viewed in detail, cardio history doesn't exist as a screen.
2. **Editing affordances.** Rename/reorder/duplicate/delete are missing almost everywhere,
   and one edit path (routine edit) actively destroys data (supersets).
3. **The AI's knowledge outruns the data model.** The prompt contains ~100 lines of
   periodization/deload doctrine the schema cannot represent, so the coach can only ever talk
   about it as prose.

### Top 10 actions, ranked

| # | Action | Why | Section |
|---|--------|-----|---------|
| 1 | Fix the superset-wipe bug in routine edit | Data loss on every edit+save, ~4 lines | §3.2 |
| 2 | Progression write-back ("apply suggested weight") | Biggest daily friction; presets don't work as advertised without it | §3.4 |
| 3 | Fix chat-history poisoning (validate new turn only) | One blocked phrase bricks the coach until history is nuked | §2.2 |
| 4 | Fill Home's missing state + make routines reachable | Fresh-account manual path currently ends on a blank screen | §4.1 |
| 5 | Surface swallowed errors (start/finish workout, etc.) | Buttons that silently do nothing read as "broken app" | §4.4 |
| 6 | Completed-session detail view | The data exists; History is a dead end without it | §4.3 |
| 7 | Cardio parity: run summary + history + Progress presence | A logged run is invisible after the fact | §4.5 |
| 8 | Exercise detail screen with media/instructions | The single most visible gap vs. every paid competitor | §5 T2 |
| 9 | Rename/duplicate/delete affordances (endpoints exist) | Unreachable server endpoints; dead client code | §3.5 |
| 10 | Periodization layer (week/block/deload in the schema) | Long-term differentiator; unlocks the AI's existing knowledge | §3.6 |

## 2. AI Coach

### 2.1 Capabilities inventory (what works today)

- Free-text coaching chat constrained by a ~350-line server-side system prompt
  (`server/app/services/ai/prompts.py`): equipment tiers, split selection, session sizing, rest
  periods, volume landmarks, warm-up protocol, limitation→substitution table, progression
  schemes, block periodization doctrine, adaptive too-easy/too-hard logic, deload triggers,
  and an intake protocol that skips questions already answered by the profile.
- Trusted DB context injected per request (`context_service.py`): full exercise catalog,
  last-30-day session summary, last completed set per exercise, current routine, bodyweight
  trend — plus a live-session block when opened mid-workout.
- Exactly one structured suggestion per reply (adjustment > program > routine,
  `client.py:108-122`), each surfaced as an explicit user-approved card: Save Routine, Save
  Program (`POST /ai/programs/accept`), or Apply Adjustment
  (`POST /ai/sessions/{id}/adjust` — swap/adjust_weight/remove/add, incomplete sets only).
- First-run auto-generation of a starter program from the onboarding profile
  (`HomeViewModel.generateInitialRoutine`).
- Guardrail stack: server-only prompt, per-turn injection screening, two-layer bounds
  (Pydantic reject + extraction clamp), catalog-resolved exercise names, ownership checks,
  6-action cap, no autonomous write path. This layer is in good shape — see §2.4.

### 2.2 Bugs and design flaws

- 🔴 **[verified] Permanent conversation poisoning.** `client.py:54-60` runs
  `validate_request` over **every** user turn in the submitted history (the correct 2026-06-03
  injection fix), but the client always resends the entire local transcript
  (`AiChatViewModel.kt:83-100`). Net effect: a single message that ever trips a blocked pattern
  makes **every subsequent request 422 forever**; the only escape is the destructive "Clear
  history" action. Fix direction: hard-validate only the *new* turn and drop (or redact)
  blocked historical turns server-side instead of failing the whole request.
- 🔴 **Unbounded single global chat thread.** `ChatMessageDao` is one table with no thread
  key, no cap, no pruning; the full transcript is re-uploaded every turn on top of the
  server-injected catalog + history + profile. On a local 8B model this silently blows the
  context window — quality degrades and latency grows monotonically with conversation age.
  The in-workout chat and the Coach tab also share this one thread, so mid-workout "swap
  bench" turns permanently pollute the general coaching conversation.
- 🟠 **Suggestion cards are in-memory only.** `_pendingRoutine/_pendingProgram/_pendingAdjustment`
  are plain `MutableStateFlow`s (`AiChatViewModel.kt:60-68`) — not in `SavedStateHandle` or
  Room. Process death or leaving the tab loses the card while the persisted assistant bubble
  still says "tap Save Program". `clearHistory()` also doesn't clear pending cards.
- 🟠 **Server error messages never reach the user.** The server maps failures to
  carefully-worded details — 504 "LM Studio timed out — the model may still be loading",
  503 "not reachable", 422 guardrail text (`client.py:80-107`) — but no `errorBody()` parsing
  exists client-side; the snackbar shows raw `HTTP 504 Gateway Timeout`.
- 🟠 **Failed sends leave a dangling user turn.** The user message is inserted into Room
  *before* the network call (`AiChatViewModel.kt:85`); on failure it stays, is resent forever
  as history, and there's no retry affordance on the bubble.
- 🟡 **The model never sees the JSON it emitted.** Fenced blocks are stripped before the reply
  is returned/stored, so a follow-up like "make day 3 easier" has no structural record of the
  program in model-visible history — the model must re-derive it, a likely source of drift.
  (Related prompt/code drift: `prompts.py` tells the model not to restate a plan it "already
  provided" — which was stripped.)
- 🟡 **Chat history survives a 401-driven sign-out.** Explicit logout clears all tables, but
  `TokenRefreshAuthenticator.signOut()` clears tokens only — the next account on the device
  inherits the previous user's coaching transcript.
- 🟡 **Reply-side sanitizer can degrade legitimate refusals.** The regex scan over the model's
  own reply replaces any match with a canned line — so a contextual, correct refusal that
  *names* a banned substance ("I can't advise on steroid dosing — see a doctor") is swapped
  for the generic text.
- 🟡 Latent smaller issues: `history = req.messages[:-1]` assumes the transcript ends with a
  user turn and `ChatRequest.messages` has no non-empty/role validation; `_resolve_exercise`'s
  partial-match fallback is `LIKE %name% LIMIT 1` with no ordering (nondeterministic swap
  targets); `POST /ai/programs/accept` is non-atomic (acknowledged in
  `program_persist.py:8-11` — mid-sequence failure orphans AI routines); `_current_plan_line`
  reports the most-recently-created routine, not the active program's current day.
- 🟡 **No streaming, no cancel.** One blocking `httpx` call (90 s server timeout / 120 s
  client read timeout); the input is disabled behind a typing indicator for the whole wait.
  For a local model writing a 6-day program that's a long dead-air period.

### 2.3 Recommendations (ranked)

1. **Fix poisoning** (above) — small server change, removes the worst failure mode.
2. **Threaded conversations**: a "new chat" action, per-workout threads for session-aware
   chat, and a rolling cap/summarization so the request size stops growing without bound.
   (One Room column + a thread id on `ChatRequest` gets most of the value.)
3. **Persist pending suggestion cards** (serialize into the message row or DataStore).
4. **Parse error bodies** in `AiRepository` so the server's good messages surface.
5. **Give the empty Coach tab starter chips**: "Build me a program", "Analyze my week",
   "Adjust today's workout" — the server already holds all the context these need.
6. **Post-workout AI debrief** on the summary screen (one `POST /ai/chat` with the session
   in context; the hook was explicitly deferred in the cardio sprint and never landed).
7. **Streaming responses + cancel** — LM Studio supports SSE; this transforms perceived
   quality more than any prompt change.
8. **Feed emitted program JSON back into model-visible history** (compact form) so
   follow-up edits work reliably.

### 2.4 Guardrails — verdict

The guardrail layer is the strongest part of the AI feature: server-side prompt, screening on
every turn, clamped extraction, catalog resolution, ownership checks everywhere,
incomplete-sets-only mutation, no autonomous writes. Nothing here needs urgent change beyond
the poisoning fix (which is a guardrail *ergonomics* problem, not a weakening). Two soft spots
worth noting for later: no post-extraction sanity check on structurally-valid-but-absurd
output (a 10×50 @ 600 lb day passes the per-field clamps), and the prompt's "4–6 exercises"
rule isn't enforced in extraction (a 1-exercise day passes).

## 3. Programs & routines

### 3.1 The three creation paths today

| Path | UX | Converges on |
|------|----|--------------|
| **AI coach** | Chat → Save Program card → auto-activated | `POST /ai/programs/accept` |
| **Presets** (10 curated) | Programs → Presets → "Use program" → auto-activated | `POST /ai/programs/accept` (as a plain persistence API) |
| **Manual** | Home "+" → CreateRoutine (once per day)… then Programs → "+" (name-only dialog) → ProgramDetail → add days from a routine dropdown → Save → back → activate | `POST /programs` + `PUT /programs/{id}/days` |

The manual path is a three-screen scavenger hunt, and on a fresh account it **dead-ends**: the
routine dropdown in `ProgramDetailScreen` renders "No routines available" with no
create-routine affordance — the user must already know to go back to Home → "+"
(`CreateProgramDialog` even admits it: *"You can add days after creating the program."*).

### 3.2 Bugs

- 🔴 **[verified] Editing a routine silently destroys its supersets.**
  `RoutineDetailViewModel.startEdit()` builds each `DraftExercise` without copying
  `supersetGroup` (`RoutineDetailViewModel.kt:92-102`), and `saveEdits()` builds
  `RoutineExerciseIn` without passing it (`:143-151`) — it defaults to null on the wire, and
  `PUT /routines/{id}/exercises` is a wholesale replace. Open any superset routine, tap edit,
  tap save without touching anything → all grouping is gone. `CreateRoutineViewModel`
  handles the same field correctly (`CreateRoutineViewModel.kt:124`), so this is a ~4-line fix
  plus a regression test. No existing test covers it.
- 🟠 **Program day breakdown goes stale after editing a routine.**
  `ProgramDetailViewModel.refreshRoutineExercises` exists precisely for this and has **zero
  callers** — `load()` sits behind `LaunchedEffect(programId)`, which doesn't re-run on
  pop-back from `RoutineDetail`.
- 🟠 **Offline-saved program days render as rest days.** `ProgramRepository`'s
  `ProgramDayIn.toEntity` sets `routineName = null` (`ProgramRepository.kt:188-191`), and
  "Rest / no routine" is the exact string used for genuine rest days — an offline-saved
  program looks like an all-rest program until a server pull.
- 🟡 **Deleting a routine silently converts program days to rest days.**
  `program_days.routine_id` is `ON DELETE SET NULL` and rest is encoded as `routine_id IS
  NULL` — there's no `is_rest` flag to distinguish "intentional rest" from "orphaned day",
  and no warning at delete time. (Moot today only because the UI has no routine-delete
  affordance at all — see §3.5.)
- 🟡 **`replace_days` doesn't validate routine ownership** (`program_service.py:127-148`) —
  another user's routine UUID is accepted and its name leaks back via `_to_out`. Personal
  app, low practical risk, but it's inconsistent with `session_service.create_session`,
  which checks exactly this.
- 🟡 **Client and server disagree on "next day" for repeated routines.** The client
  projection uses `indexOfFirst` (`WorkoutProjection.kt:120`), the server's `get_next_day`
  uses the *last* match — Home/Calendar and the server's suggestion can diverge. The known
  real fix (persist `program_day_id` on `WorkoutSession`) has been in the backlog since
  2026-06-03.

### 3.3 Structural gaps in the data model

- **No program metadata.** `WorkoutProgram` is `id, user_id, name, is_active` — no
  `created_at`, no `source` (ai/preset/manual; routines have one, programs don't), no
  description, no duration, no start date. Consequently: no provenance ("created from
  StrongLifts"), no sorting by recency, no "week 3 of 8", no program history.
- **No schedule on the program.** Cadence is one global client preference
  (`workoutCadenceDays`) applied to whatever is active — no weekday schedule (Mon/We/Fr), no
  per-program cadence. Whether a program is cadence-driven or rest-day-driven depends on
  whether its author happened to include rest days.
- **No periodization structure.** A program is a flat, infinitely-cycling day list. The AI
  prompt carries ~100 lines of block/deload doctrine (`prompts.py:137-234`) it cannot encode —
  the coach can describe a deload week but never schedule one.
- **Routine exercises lack**: rep ranges (single int only), per-exercise rest interval,
  RPE/RIR, per-exercise notes.
- **Room PK `(routineId, exerciseId)`** silently collapses duplicate exercises on sync — the
  server and the AI both legitimately produce top-set/back-off structures the client then
  eats. Known backlog item; it will bite any periodization work first.

### 3.4 Progression — the engine is good; nothing consumes it

The double-progression engine (`app/progression.py`) is correct and well-tested: `add_weight`
only when all sets hit target reps, else `add_reps`; deload at 90% after 3 stalled sessions;
Epley e1RM + PR flag.

**But it never writes anything.** 🟠 **[verified]** `create_session` seeds every set from the
static prescription (`session_service.py:93-104` — `weight=pe.target_weight`), and the client
renders the suggestion as a display-only chip (`WorkoutScreen.kt:487` → `progressionUi`);
`suggestedWeight` is otherwise used only to seed the warm-up/plate dialogs when a set has *no*
target (`:435`) — which for a weighted routine is never. The only writer of
`RoutineExercise.target_weight` in the entire server is the AI adjustment path.

Net effect: **StrongLifts 5×5 pre-fills 95 lb forever** with a chip politely suggesting
"add 2.5 lb" that the user must act on by retyping every set, every session. For presets whose
entire premise is "add weight each session", this is the single biggest friction point in the
app. Also worth noting: a user who completes all sets but stays short of target reps forever
never accumulates toward a deload (`_count_stalls` counts only incomplete-set sessions), and
progression hints are unavailable offline (accepted gap).

**Recommendation:** an "Apply" affordance on the progression chip that (a) updates this
session's incomplete sets and (b) optionally writes back to the routine — exactly the
mechanics the AI adjustment path already implements server-side. This is the highest
value-per-effort feature in the whole audit.

### 3.5 Missing affordances (endpoints already exist)

- Routine **rename/delete**: `PATCH/DELETE /routines/{id}` exist; `HomeViewModel.renameRoutine`
  / `.deleteRoutine` are dead code (orphaned when Sprint 5 removed Home's routine list); no
  surface offers either. Routines are effectively immortal and unnameable.
- Program **rename**: `PATCH /programs/{id}` supports it; no UI anywhere.
- Program day **label edit**: fixing a typo means delete + re-add (and losing position).
- **Duplicate** routine/program: doesn't exist; it's how most people build an A/B split.
- **Exercise reordering** in the routine editor: `order` is list position; the only way to
  reorder is remove-and-re-add at the end. (Days have move up/down; exercises have nothing.)
- **No unsaved-changes guard** on `ProgramDetailScreen` (back = silent discard), and its list
  keys by index, which fights the reorder buttons.

### 3.6 Presets — good content, rough edges

- **No preview**: the card shows a comma-joined exercise list; sets/reps/weights are
  invisible until after applying.
- **Always force-activates** and silently deactivates the current program; no "save without
  switching".
- **No dedup**: applying twice duplicates the program *and* all its routines.
- **No rest days in any of the 10 definitions** — so descriptions like "~3×/week" are
  unrelated to the actual schedule (which is the global cadence pref).
- Unresolved exercise names are silently dropped (`mapNotNull`); the user is only told if an
  entire day comes up empty.
- No cardio or strength+cardio combined presets, even though the cardio module exists.
- Strength active-program is server state; cardio active-program is a client DataStore pref —
  two unrelated mechanisms merged at projection time, no same-day conflict detection, and
  cardio programs never appear on the Programs screen.

### 3.7 Recommendations (ranked)

1. Progression write-back (§3.4). 2. Superset-wipe fix (§3.2). 3. A unified program-builder
flow — at minimum "create new routine" reachable from inside `ProgramDetailScreen`. 4. The
§3.5 affordances (mostly UI over existing endpoints). 5. Program metadata + weekday schedule.
6. Preset preview + rest days + non-activating add + dedup. 7. Persist `program_day_id` on
sessions. 8. A periodization layer (`week`/`block`, or a `ProgramWeek` table with volume
modifiers) — the long-term differentiator that lets the AI author what it already knows.

## 4. Layout & flow

The shell is sound: 5 tabs (Home · Calendar · Cardio · Coach · Progress), 24 routes, all
registered and reachable, consistent chrome rules, a resume strip that survives process
death. The issues are in specific flows.

### 4.1 The fresh-account manual path ends on a blank screen

- 🟠 **[verified] Manually created routines are unreachable.** `Screen.RoutineDetail` has
  exactly one navigation source: the "Edit workout" link inside an expanded program day
  (`ProgramDetailScreen.kt:146`). Home's "+" → `CreateRoutineScreen` → save → pop to Home —
  which renders **programs only**. The new routine exists but has no screen that opens it
  until it's attached to a program day.
- 🟠 **[verified] Home has a missing state.** The `when` at `HomeScreen.kt:263-296` covers
  (no programs ∧ no routines), (generating), and (programs non-empty) — the state *programs
  empty ∧ routines non-empty* (exactly what §4.1 produces) renders **nothing** below the
  stats. Combined effect: create a routine on a fresh account → blank Home, routine
  unreachable.
- 🟠 **Presets are near-undiscoverable when the AI is down.** With zero programs, Home shows
  no "Your programs" header → no "Manage" link → the Programs screen is unreachable from
  Home; the Settings "Programs" section renders as plain text (no nav row) when empty. The
  only route to the 10 presets is Calendar → "No active program" card → Programs → Presets.
  Home's sole empty-state CTA is "Chat with AI Coach", and the first-run auto-generate
  swallows failure silently — so a new user with LM Studio down sees a dead app that
  actually contains 10 ready-made programs.
- 🟠 **[verified] Reset Account never re-onboards.** `SettingsViewModel.resetAccount()`
  calls `clearOnboarding()` (KDoc: "on next sign-in the user is sent back through the
  onboarding questionnaire") — but `AuthViewModel.login()` and `completeSuiteLogin()` call
  `setOnboardingDone()` unconditionally (`AuthViewModel.kt:77,131`) before `LoginScreen:56`
  reads the flag. Onboarding is reachable only from Register; after a reset the app instead
  auto-generates a program from an empty profile.

### 4.2 Recommended fix shape for §4.1

Restore a "Your routines" section on Home (or land `CreateRoutine` → `RoutineDetail`), fill
the missing `when` branch, add a "Browse presets" button to Home's empty state alongside the
AI CTA, give the Settings Programs section a nav row when empty, and route post-reset login
through the onboarding gate.

### 4.3 Dead ends after the fact

- 🟠 **No completed-session detail.** `SessionHistoryScreen` navigates only for
  `in_progress` sessions; a completed one expands to names + done/total counts. The actual
  reps/weights are one `GET /sessions/{id}` away and never shown. Every commercial app has
  this screen.
- 🟡 **No per-exercise history mid-workout** — one prior session is shown; the exercise name
  isn't tappable for full history/chart.

### 4.4 Errors that are computed and then discarded

- Home `startSession` sets an error state that the screen reads only for `Loading` — tapping
  "Start" with the server down does nothing visible, forever (`HomeViewModel.kt:443` /
  `HomeScreen.kt:105`).
- Workout `finishSession` failure is likewise silent (`WorkoutViewModel.kt:315` /
  `WorkoutScreen.kt:95`).
- Calendar `startProjectedSession` swallows the exception outright; both `logBodyweight`
  implementations `catch (_: Exception) {}`.
- `ErrorState(onRetry)` exists in the component library and is **never passed by any call
  site** — zero error states in the app have a retry button.
- Progress → Strength stacks two full-size empty states in one column and leaves its error
  state unhandled (`ProgressScreen.kt:433-578`).

These are cheap fixes (the snackbar hosts already exist) with outsized perceived-quality
impact: silent buttons are what make an app feel broken.

### 4.5 Cardio is a second-class citizen

Finishing a run swaps the center label to "COMPLETE" — no summary screen, no stats, no
celebration (compare `WorkoutSummaryScreen`). There is **no cardio history view anywhere**
(a comment in `ManualCardioScreen.kt:73` refers to one that doesn't exist — manual entries
vanish into the streak numbers), and cardio has no presence in Progress. Minimum parity: a
run summary screen, cardio rows in History (or a list on Cardio home), and a cardio panel in
Progress.

### 4.6 Smaller polish items

- Two different bodyweight dialogs — Home's logs weight only, Progress's logs weight + body
  fat + 6 measurements; the "Log weight" launcher shortcut routes to the lesser one. Unify.
- Resume strip filters `date == today` (`ActiveWorkoutStore.kt:22-23`) — a workout started
  before midnight vanishes from the strip at 12:00am.
- Duration formatting: `WorkoutScreen`/`WorkoutSummaryScreen` render 75 minutes as `75:00`
  (`SessionHistoryScreen` does it correctly).
- Deep-link/notification navigation lacks `launchSingleTop` — repeated taps stack duplicate
  Workout/CardioRun entries.
- `android:usesCleartextTraffic="true"` applies to release builds.
- Dead code: `HomeViewModel.deleteRoutine`/`renameRoutine`/`routineExercises` (orphaned by
  Sprint 5) and `nextProgramDay` — the last still fires a network call on **every** sync
  round for a value nothing collects.
- Stale docs: "four bottom-bar destinations" KDocs (there are five); CLAUDE.md claims a
  workout "inline edit mode" and a Home-browsable exercise library that no longer match the
  code.

## 5. "Worth money" — tiered feature roadmap

### Tier 1 — make what exists land (mostly fixes, days not weeks)

An app feels premium when nothing dead-ends and nothing fails silently. This tier is the
verified-bug list: superset wipe, progression apply, chat poisoning, Home blank state +
routine reachability + preset discoverability, error surfacing with retry, completed-session
detail, cardio summary/history. Shipping only this tier would change the app's perceived
quality more than any new feature.

### Tier 2 — table stakes vs. Hevy / Strong / Boostcamp

- **Exercise detail screen**: instructions, primary/secondary muscles, demo image or short
  video, per-exercise history + PRs. Requires new `Exercise` fields, an asset pipeline, and
  an image loader (Coil) — currently there is no image pipeline at all. Highest-visibility
  gap vs. every paid competitor.
- **Set types**: warm-up / drop / failure / AMRAP flags on `SetLog` (the warm-up dialog is
  advisory-only today and logs nothing).
- **RPE/RIR** per set (also unlocks smarter progression + honest deload detection for the
  "completes all sets but grinds" user, §3.4).
- **Manual mid-workout exercise management**: add/remove/reorder/swap by hand — today the AI
  is the only path, and there's no set deletion at all.
- **Rest-timer controls**: +15/−15 buttons, per-exercise override, auto-start toggle.
- **Per-exercise history/chart accessible from the workout screen.**
- **Health Connect** integration (sessions + bodyweight out, steps/HR in) and **data export**
  (CSV/JSON from Settings). Both are trust features: people pay for apps they don't feel
  locked into.
- **Cardio GPS/pace** (already on the roadmap as deferred).

### Tier 3 — differentiators that justify "paid" (the AI is the moat)

Spotter's unfair advantage over Hevy/Strong is a private, guardrailed coach with full access
to training history. Lean into it:

- **Post-workout AI debrief** on the summary screen and a **weekly AI recap** — the suite's
  digest infrastructure (Dragonfly) already pulls Spotter's week; an in-app version closes
  the loop.
- **Periodized programs the AI can actually author**: once §3.6's schema lands
  (weeks/blocks/deloads), the coach's existing doctrine becomes a scheduling feature no
  competitor's static templates match — auto-scheduled deloads, block transitions, "week 3
  of 8" on Home.
- **Proactive coaching driven by real signals**: stall detected → the nudge suggests a chat;
  streak-at-risk and PR-celebration notifications; "you've deloaded squat twice this month —
  want to talk about it?".
- **Preset preview → program marketplace feel**: full day-by-day preview screens for
  presets (and AI programs before accepting), with muscle-group balance visualization.
- **Templates from history**: "repeat last workout" / save any completed session as a
  routine.

## 6. What's genuinely strong (keep, don't churn)

- The timer architecture (`WorkoutTimerController`, `CardioRunController`, `TimeProvider`) —
  drift-free, background-correct, process-death-safe. Better than most shipping apps.
- Offline model: write-through + drain queue, id translation on sync, exercise-catalog
  mirror, stale banners with the IOException-vs-HttpException degrade rule.
- The AI guardrail stack (§2.4) and the suggestion-card trust model (AI proposes, user
  applies) — the right architecture; every recommendation above builds on it rather than
  changing it.
- The progression *math* — it just needs a write path (§3.4).
- PULSE: coherent, distinctive, consistently applied; the design system is already at
  paid-app quality.
